Product tour · 17 stops

k8boss-admin

A Kubernetes console that will not tell you something it does not know.

It browses every resource a cluster serves, and it changes them through a path that preflights the permission, dry-runs the write, shows you a diff, waits for your confirmation, and records what happened — including what failed. It holds no cluster state: every page you are about to see is a live read.

What follows is the console as an operator meets it, in the order they meet it. Every image is a real screenshot of the running build.

Cluster prod-eu · v1.31.4 Console 0.1.0 Writes enabled Shot production build, every API call mocked

The cluster in these screenshots is having a bad morning

That is deliberate. A tour is where a console usually starts lying: every table full, every number green, every read successful. This one is shot against a fixture cluster mid-incident, with reads that failed — because the failures are where the product's argument lives.

So: payments is crash-looping, one node's pod listing was refused, the metrics.k8s.io APIService is down, and a DaemonSet controller has gone quiet. Watch what the console does with each of those, and in particular watch what it does not claim.

A number this console could not derive renders as —, never as 0.

A node showing zero requested cores and zero pods reads as idle, and an idle node is the one an operator picks to drain.

Part one

Reading a cluster

Six surfaces, and one rule running through all of them: an empty list means the cluster has none of the thing. A read that could not happen says so, by name.

01

Overview

Rule 1 Empty is never blind

The landing page is six independent collectors. One failing sets its own key to null and names itself in the banner; the other five are unaffected. There is no code path here that turns a missing measurement into a small one.

  • Five dashes, no zeroes. CPU capacity, CPU requested, memory capacity, memory requested and pod capacity all derive from the node listing, and that listing was refused. Each renders as — with a tooltip saying the read never happened.
  • The banner names its sources. Not "some data is missing" — core/nodes and metrics.k8s.io/nodemetrics, each with the reason. It is persistent, not a toast: a toast expires while you are still working out why a tile is blank.
  • A missing API is not an error. metrics.k8s.io is absent, and the row says "not present on this cluster. Nothing is wrong". Rendering ordinary facts in red trains people to ignore red.
02

Nodes

Rule 1 A number we could not derive is null, never zero

Capacity, allocatable, and what the scheduler has actually committed. The column this page exists for is requested / allocatable, and the reason it is built the way it is fits in one row of the table.

  • ip-10-0-1-6 is the point. Its pod listing failed, so requested CPU, requested memory and pod count are —. Had they rendered as 0, that row would be the most attractive node on the page to drain.
  • Cordoned is not a health state. ip-10-0-2-11 carries both Ready and Cordoned, because it is both. One badge does not replace the other.
  • Requests, not usage. The subtitle says so outright: this console reads no metrics API, and it does not imply otherwise by labelling a request as a measurement.
03

Workloads

Defect standard A wrong answer delivered confidently is worse than no answer

Deployments, StatefulSets, DaemonSets, Jobs, CronJobs and ReplicaSets in one table — because an operator asking "what is broken in prod" does not think in terms of which controller owns the pods.

  • Unknown is a required status, and it is not green. The log-shipper controller has not written a status for the current generation, so it has told us nothing. Its ready count is — and its status is grey. Reporting that as Healthy would make a green row a lie.
  • Suspended is a settled state. nightly-report is suspended on purpose, so it is not surfaced as a problem — but it is also not disguised as healthy.
  • Every status carries its reason. "1 of 5 replicas not available" sits under the badge, so the table answers the follow-up question before it is asked.
04

Pods

Defect standard Phase lies, so the console reads past it

A Running pod whose container is in CrashLoopBackOff is not running. The backend supplies phase_detail for exactly the cases where the Kubernetes phase is the wrong answer, and this page renders the detail over the phase.

  • The filter matches the detail too. Filtering to "Running" and being shown a crash-looping pod would reintroduce the lie one layer up.
  • One restart count is —, the other is 47. A pod in CrashLoopBackOff showing "0 restarts" is a confident wrong answer; showing a dash is an honest one.
  • Terminating is a phase_detail too. A pod being deleted still reports Running right up until it is gone.
05

Namespaces

Rule 1 Empty is never blind

The same rule, in the place where breaking it is most expensive. An operator reading "this namespace has no pods" acts on it — during a cleanup, that means deleting the namespace.

  • A dash in a "safe to delete?" column. Nothing on this page can turn "we could not look" into a small number.
  • Terminating namespaces are shown as such. legacy-batch is on its way out and says so, rather than appearing as an ordinary Active namespace.
06

Events

Rule 1 An empty table is "nothing recently", never "nothing ever"

Type, namespace and involved object become a server-side fieldSelector, so the newest matching events come back rather than the newest events of which a handful match. Sorting is the backend's, and events with no derivable timestamp sort to the bottom — an unknown age must not present as the most recent thing that happened.

  • The window is the cluster's, not the console's. The API server keeps events for about an hour by default, and the page says so rather than implying it has the full history.

Part two

Changing a cluster

Every write in this console — scale, restart, suspend, rollback, cordon, drain, create, replace, delete — goes through one function, in one order. Not a convention that twelve endpoints follow, because a convention followed by twelve endpoints is a convention nine of them follow after the next refactor.

  1. 1 · Gate
    Is this deployment allowed to write at all?
  2. 2 · Preflight
    A SelfSubjectAccessReview for this exact verb and object.
  3. 3 · Apply
    dryRun=All first — same URL, same body.
  4. 4 · Diff
    The API server's own projection, as a unified diff.
  5. 5 · Audit
    Every terminal state, including the refusals.
07

The form

Rule 2 Every mutation is preflighted

Before the dialog opens, the page has already asked the API server whether you may do each of these things. An action you cannot perform is disabled with the reason — not hidden, and not offered and then refused.

  • "Scaling sets an absolute replica count, not a delta." The one sentence that stops a 5 becoming a 13.
  • An unknown current count does not become a starting value. When the controller has not reported replicas.desired, the field starts empty and Preview is disabled with the reason. Seeding it with 0 would put a working workload one unread click from nothing.
  • Suspend is greyed here. A Deployment has nothing to suspend, and the tooltip says that rather than "you may not do this" — which would send you to grant a permission that would not help.
08

The diff

Rule 3 Every mutation can be dry-run, and the destructive ones must be

This is the load-bearing surface of the whole console. dryRun defaults to true on every write body; the console sends dryRun=All as a query parameter on the same call the real write would use, and renders the API server's own projected object as a unified diff. Whatever is on this screen is what you are consenting to.

  • "Nothing has been applied yet." Stated on screen, because a successful dry run returns a full object, a resourceVersion and a diff — everything that otherwise looks like success.
  • The form is gone. Once a diff is on screen the inputs no longer exist, so there is no state in which you can change the number and then confirm a diff projected for a different one. Editing means going back, which discards the diff and requires a fresh dry run.
  • The + and − stay in the text. Colour is reinforcement, never the only signal — for greyscale, for colour-blind readers, and for anything pasted into a ticket.
  • Line numbers come from the hunk headers. A unified diff omits everything outside its context window, so counting from the top would print confident, wrong line numbers for every hunk after the first.
09

Applied

Rule 3 applied is true only when the write actually landed

The confirming call is the same request with dryRun: false. Only now does the response carry applied: true, and only now does the console report success — from a phase that is reachable no other way.

  • It links to its own audit record. The write and its trail entry are reachable from each other.
  • A no-op offers no confirm button at all. If the API server compares your request to the live object and finds no difference, confirming would produce an audit row and a success toast for a write with no effect.
  • A 409 re-runs the dry run. If the object changed while you were reading, nothing is written: the console adopts the server's resourceVersion, re-projects against the object as it now is, and puts the new diff in front of you. What you approved the first time is discarded, not resubmitted.
10

Drain

Defect standard "Drained" over three stuck pods gets a machine terminated

A diff of unschedulable: false → true is an accurate description of the patch and tells you nothing about the twenty pods about to be evicted off the machine. So a drain returns a plan alongside the diff: every pod classified evict, skip or blocked, with a reason, whether or not anything runs.

  • Blocked pods stop the drain. pg-primary-0 is held by a PodDisruptionBudget; adhoc-query-shell has no owning controller, so nothing would recreate it elsewhere. Both are named, with the reason, before anything happens.
  • force means "I have read this plan and I accept it". It does not defeat a PodDisruptionBudget — the API server enforces those on the eviction subresource — and the checkbox's own help text says so. Claiming otherwise would sell a bigger hammer than exists.
  • Changing an option re-runs the dry run. A plan projected without Delete emptyDir data is not the plan that would run with it.
  • Evictions are reported per pod. A drain over three pods the API server refused comes back applied: true with failed: 3 and drained: false — never a bare success.

Part three

The long tail

The parts of a cluster nobody wrote a page for, the manifest behind every object, and the two records that answer "who tried".

11

API explorer

Rule 1 A missing group must not look like a cluster with fewer resources

This is why the console can administer a cluster it has never seen. Anything the cluster serves is reachable through the dynamic client — a Certificate, a Kafka, an Argo CD Application — with its YAML readable and editable through the same audited, dry-run-first path as everything else.

  • "Unreachable", not absent. An operator who cannot find certificates.cert-manager.io in this list must be able to tell "this cluster has no cert-manager" from "cert-manager's APIService is down". Backwards, that sends someone to install what they already have.
  • Verbs are shown per resource. What you can do to a kind is a property of the cluster, and it is on the row.
12

YAML

Rule 4 Optimistic concurrency is mandatory on update

Every object's manifest, rendered the same way, wherever the object is. Each panel says when it was read, re-reads on a timer, and has a Reload button for when a timer is not fast enough.

  • PUT carries the resourceVersion you were looking at. A mismatch is a 409 with a fresh diff against live, never a blind overwrite. Two operators on the same Deployment during an incident is the case this exists for.
  • A failed refresh keeps the manifest and says the refresh failed. It does not present an older copy as current.
  • An object that changes while you are editing raises a warning. It does not quietly rewrite your edit.
13

Audit

Rule 5 Every write is audited, including the ones that failed

Actor, cluster, verb, target, dry-run flag, diff digest, outcome — on every terminal state. A trail holding only the writes that worked answers "what changed" but not "who tried", and after an incident the second question is the one being asked.

  • The verdict is partial, and it is not dressed up as a pass. Twelve records predate the hash chain. They are never back-filled — hashing them now would attest whatever they say today, turning "we do not know" into "verified". The console counts them and withholds the verdict.
  • The denials are as visible as the applies. contractor.j tried to delete prod/payments and was refused at preflight. That row exists precisely because nothing happened.
  • Sign-ins share the trail. They carry no cluster at all, which is why the scope filter has a third position — without it every authentication record would be invisible from a session with a cluster selected.
  • Hash-chained, and honest about what that buys. Chaining prevents nothing; it makes a psql-level edit detectable. That is the strongest honest promise an application can make about storage it does not own.
14

Clusters

Rule 2 A clean denial and a failed review are different facts

Registration, connection test, and the baseline permission matrix. The page exists to answer one question at the moment it is cheapest to answer: will this ServiceAccount actually work? "The token is valid" and "the token can do the job" are different facts, and only the first one is easy.

  • An unreachable cluster reports permissions: null. Not an empty list — that would claim the ServiceAccount holds none of the baseline permissions, which is a statement about RBAC the console never got close enough to make. It renders as "not checked", with the connection error stated.
  • A failed review is a third state. allowed: false with a non-null evaluationError means the SelfSubjectAccessReview itself failed — grey "unknown", never a red "no". Conflating them tells an operator they lack a permission they may well hold.
  • Tokens are encrypted at rest, and nothing about a permission is ever cached: a cached allowed outlives the RBAC change that revoked it.

Part four

The console itself

Three things that are true of every page above, whichever one you are on.

15

Read-only

The default posture. A banner, a masthead badge, and every write control disabled — never rbac_denied, because the operator's permissions are irrelevant and saying otherwise sends them to fix the wrong system. Dry runs still work.

16

Sign-in

Optional local, LDAP or OpenID Connect authentication, with sign-in throttling; legacy proxy mode remains available when it is disabled. Sign-ins and sign-outs are recorded in the same trail as cluster writes.

17

Dark mode

The whole console, including the diff tints and every status badge, has a second palette. The +/− markers survive it, because colour was never carrying the meaning on its own.

Reference

The error vocabulary

One exception class per stable code, because the frontend branches on the code rather than on words in a sentence. It disables a button on rbac_denied, offers refresh-and-retry on conflict, renders "not present on this cluster" on unsupported, and shows a global banner on mutations_disabled.

CodeHTTPWhat it means, and what it does not
no_cluster_selected409No cluster id, and nothing registered.
cluster_unreachable502DNS, TCP, TLS or deadline. We never got an answer, so nothing about the cluster's contents can be inferred.
rbac_denied403Preflight said no, or the API server did. Names the missing permission.
not_found404The object or the API resource does not exist.
conflict409resourceVersion mismatch. Comes back with a fresh diff, not a retry.
invalid422Schema, admission or request validation refused it. Nothing was written.
mutations_disabled403The deployment is read-only. Deliberately not rbac_denied — your permissions are irrelevant here.
unsupported501The cluster does not serve that API. Not an error in the UI: no Ingress CRDs and no metrics API are ordinary facts.
upstream_error502Anything else, including 401 — the cluster answered, and it refused us.

Codes map by HTTP status, not by Status.reason: the reason string is not stable across API server versions or admission webhooks, and the status code is part of the Kubernetes API contract.

How these screenshots were made

Every image on this page is a real screenshot of the k8boss-admin frontend, captured from a production vite build served by vite preview — not the dev server, and not a mockup. The console is driven by Playwright with every /api/** call intercepted, so no backend and no cluster are involved.

The capture script and its fixture cluster live in the repository at frontend/tools/tour-shots.mjs and frontend/tools/tour-fixtures.mjs. Run node tools/tour-shots.mjs against a running preview server to regenerate the set. That is the point of shooting it this way: when the console changes, the tour can be re-shot rather than re-drawn.

The fixtures deliberately carry failed reads — a denied node listing, a down APIService, a controller that has not reported. Each null in them is annotated with the rule it exercises, so a fixture that quietly became a 0 would be a visible change in review.

Where the rest of the truth lives

docs/api-contract.md is normative — paths, field names, error codes, envelopes. docs/safety-model.md is the document this product is judged on: preflight, dry-run, diff, optimistic concurrency, drain, audit and read-only, each with the failure it prevents. docs/rbac.md lists every permission by feature, with the degradation from withholding it.
